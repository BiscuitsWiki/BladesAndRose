# 《血与刃的白蔷薇》表现层改造方案

> 状态：**进行中**（§2 已拍板 10 项决策；§9 步骤 1 部分完成——7 张卡面画心已产出并逐像素验证、步骤 5「卡面接入」已完成、步骤 6 四项动效触发已确证）｜最后更新：2026-10-15｜关联文档：[DESIGN.md](./DESIGN.md) · [RULES.md](./RULES.md) · [SKILL-LOADOUT-PLAN.md](./SKILL-LOADOUT-PLAN.md) · [DEPLOYMENT.md](./DEPLOYMENT.md) · [PROGRESS.md](./PROGRESS.md)

本文说明「把现有的功能验证型界面改造为 2D 精美插画风」的实现方案，并预留微信小程序作为第二个表现层。

---

## 1. 背景与目标

- **现状**：功能已完整（纯规则引擎 216 个单测、boardgame.io 联机、房间与座位、账号体系、AI 托管），但界面是开发者验证向的：单色暗底 + 文字标签 + emoji 符号（✿ ❀ ⚔ 👁）拼出来的卡牌，玩家区是纵向列表，没有场景感。
- **本次目标**：**2D 精美插画风**——完整 UI 设计、角色立绘、桌椅场景、动画与音效。
- **长期目标**：同一套引擎与服务器，支撑 **Web（主）+ 微信小程序（第二客户端）** 两个端。
- **不做**：不引入游戏引擎（Godot / Unity）；不改规则、不改联机协议、不新增玩法。

## 2. 已拍板的决策

| # | 决策 | 理由 |
|---|---|---|
| 1 | **不换引擎**，只重做表现层 | 规则引擎零框架依赖、双端可共用；换引擎等于把 216 个测试、联机、房间、账号、AI 托管全部重做 |
| 2 | **2D 精美插画风**（非 3D） | 3D 才需要真 3D 管线；本作是回合制状态机，没有物理与实时性 |
| 3 | 目标端 = **Web + 微信小程序** | 小程序免安装、可在微信群里直接分享房间，对「朋友开黑」是最优入口 |
| 4 | 引擎层**零改动**（最多新增视图派生纯函数） | 现有 216 个用例是硬回归基线 |
| 5 | 美术资源**双端共享** | 两端渲染代码各写一套，但资源与场景布局数据必须共用 |
| 6 | 渲染技术**继续用 DOM + CSS + SVG**，本期不引入 Canvas/WebGL | 见 §6.1 |
| 7 | 卡面采用**单主体简略图**（每张一个居中主体），不做全身人物构图 | 全身人物在 68×102 的实际手牌尺寸下认不出（实测：巨刃近乎黑块、信者主体过小）；单主体在小尺寸下才立得住 |
| 8 | 卡框（金线 + 角饰 + 卡名条）**由程序画**，不烘进画心 | 烘进图里的边框会被卡槽裁掉（实测：手牌槽上下裁 4.6%、结算槽左右裁 3.4%），且 AI 无法为多张卡产出完全一致的边框 |
| 9 | 卡片比例统一 **2:3**（实体扑克牌比例），手牌槽由 78×100 改为 78×117 | 原槽位 1:1.28 与竖版画心（1:1.4）冲突，`cover` 裁掉约 23%；改 2:3 后降到约 3% |
| 10 | 美术资源来源 = **AI 生成 + 人工审阅 + 逐像素校验** | 见 §5.4「产出流程与硬约束」 |

## 4. 总体架构

```
                         ┌────────────────────────┐
                         │  engine（纯函数）         │  ← 零改动
                         │  规则 / playerView 过滤   │
                         └───────────┬────────────┘
                                     │ GameView（已按座位过滤）
                    ┌────────────────┴────────────────┐
                    ▼                                 ▼
      ┌──────────────────────────┐      ┌──────────────────────────┐
      │ Web 表现层（React）        │      │ 小程序表现层（WXML）       │  ← 阶段三
      │ DOM + CSS + SVG           │      │ WXSS + Canvas 2D          │
      └────────────┬─────────────┘      └────────────┬─────────────┘
                   └────────────────┬────────────────┘
                                    ▼
             ┌───────────────────────────────────────────┐
             │ 共享层（平台无关）                            │
             │ · scene.ts   场景布局 / 视觉映射（纯函数）      │
             │ · 动效编排纯函数（时长 / 顺序 / 去重）           │
             │ · 美术资源（图集 / SVG / 音效）                 │
             └───────────────────────────────────────────┘
```

**分层职责**：

- **引擎层**：不动。`playerView` 仍然是唯一的隐藏信息边界，表现层不得自行推断任何未下发的信息。
- **共享层（新增）**：把「谁在哪个位置、这张牌长什么样、现在该高亮谁」这类**可序列化的视觉映射**做成纯函数——这是双端唯一值得共用的代码（见 §6.3）。
- **渲染层**：各端各写一套。**明确放弃**「一套跨端渲染抽象」——两端的渲染与动效 API 差异大，抽象成本远高于各写一遍。

## 5. 视觉方案

### 5.1 场景构成（牌桌视图）

从「纵向列表」改为「以桌面为中心的环绕式场景」：

```
        ┌──────────────── 桌面（桌布纹理）────────────────┐
        │              [席位 3]   [席位 4]               │
        │     [席位 2]                            [席位 5]│
        │              ┌──────────────────┐              │
        │     [席位 1] │  中央版图          │  [席位 6]    │
        │              │  献祭区│弃牌区│血刃区│              │
        │              │  轮次轨道 · 花苞计数  │              │
        │              └──────────────────┘              │
        │     [席位 9]                            [席位 7]│
        │                  [席位 8]                      │
        │           ★ 自己的席位（底部居中）                │
        └────────────────────────────────────────────────┘
                 ───────── 你的手牌（扇形展开）─────────
```

- **自己固定底部居中**：视角随座位旋转（`自己 → 顺时针` 重排），每位玩家看到的都是自己在下方的桌子——这需要一个 `seatLayout()` 纯函数（§6.3）。
- **中央版图**：现在的三栏（献祭区 / 弃牌区 / 血刃区）收进一块底板，花苞计数与轮次轨道贴在底板下沿。
- **手牌区**：底部扇形/弧形排列，选中时抬起并放大；`pendingRedraw` 时切换为「替换模式」提示。
- **席位卡**：头像 + 昵称 + 手牌数 + 水晶 + 持币硬币 + 状态标签；眼睛标注（睁眼/闭眼）移到卡片左上角角标。

### 5.2 信息密度取舍

席位卡要承载的信息（全部来自现有 `player-line`）：眼睛标注、座位号、头像、昵称、「（你）」、手牌数、水晶、持币硬币、最多 8 种状态标签（必须出牌 / 随机出牌 / 必须跳过 / 必须换牌 / 可殿后 / 行动绑定 / 已出牌 / 已跳过）、断线与 AI 托管。

**资源规范**：

- 目录：`public/assets/{cards,avatars,table,ui,audio}/`（Vite 静态目录，构建时原样进 `dist`）。

### 5.4 卡面形制（已定稿）

卡面 = **上半「画心面板」+ 下半独立「卡名条」**，整体 2:3。这样卡名文字永远清晰、且不会被卡槽裁切。

```
┌───────────────────────┐  ← 卡片 2:3（手牌桌面 78×117 / 手机 68×102 / 结算 96×144）
│  ╭─────────────────╮  │
│  │ 画心（cover 填充）│  │  ← 面板内 1px 金线（#d8b26a，70% 不透明）
│  │  四角纯装饰卷叶   │  │  ← 角饰只含弧线与圆点、不含直线，故不会与金线错位
│  ╰─────────────────╯  │
│  │   卡名（程序渲染） │  │  ← 独立一条，不覆盖画心
└───────────────────────┘
```

- **画心用 `background-size: cover`**：主体居中，故即使比例微差也只会裁到边缘。
- **卡名由程序渲染**：不改图、不重出，改文案零成本。
- 实测：手牌手机尺寸 **68×102** 下 7 个图仍一眼可辨（这是真正的验收尺寸）。

**产出流程与硬约束**（AI 生图的血泪经验，后续所有卡面共用）：

1. **「武器 + 血」会被安全策略拦截**——无论写「鲜血」还是温和的「干涸血渍」都拦。换词无效，故涉及血的视觉一律**由程序画**（矢量、可控、小尺寸不糊）。血迹方案后按需求整体移除。
2. **结构性要求必须用「构造性空间描述」**，不能用方向词。例：要剑尖朝上，写「剑首与短柄在腰际，整条刃向上越过胸口，剑尖在最上缘；手下除短柄外什么都没有」——写 `pointing up` 会被无视（实测把剑画成上下都有刃）。
3. **出图后必须逐像素校验**，不能目测。方法：本机 Python + PIL 逐行采样（亮像素/轮廓阈值），量出主体几何（中心线、宽度剖面、尖端坐标），用来①判断形制是否达标（例：刃身是否「刃根最宽向刀尖单调收窄」）②定位程序叠加元素（例：血迹要贴在刃上，需按实测中心线摆）。
4. **提示词里禁止项要显式列出**（`no second blade / no reflection / no shadow blade / no ornaments` …），否则模型会自行补元素。


## 6. 技术方案（Web）

### 6.1 渲染与动效技术选型

| 候选 | 结论 | 理由 |
|---|---|---|
| DOM + CSS + SVG | **采用** | 文本渲染、可访问性、调试成本都最优；10 人局的 DOM 规模完全可控 |
| Canvas 2D（PixiJS 等） | 不用 | 只有在节点数上万或需要逐帧逐像素控制时才划算；本作是回合制 |
| WebGL / three.js | 不用 | 与「2D 插画风」的既定方向不符，且改造成本高 |
| 动效库（Framer Motion / GSAP） | 不用 | 体积与依赖成本；且小程序端无法复用——纯 CSS/WAAPI + 测量式飞行已能覆盖全部需求 |
| CSS 过渡 / 动画 / Web Animations API | **采用** | 零依赖、可被 `prefers-reduced-motion` 统一关闭 |

### 6.3 共享层：场景纯函数（唯一值得双端共用的代码）

沿用 `revealAnim.ts` 已经验证过的模式——**「决定做什么」是纯函数，「怎么画」各端自己写**：

| 纯函数 | 签名（示意） | 用途 | 双端 |
|---|---|---|---|
| `seatLayout` | `(selfSeat, count) → { id, x, y, angle }[]` | 视角旋转 + 归一化坐标（0–1） | 共用 |
| `seatVisualOf` | `(player) → { tokens, crystalState, coinOwner }` | 把玩家状态映射为视觉标记 | 共用 |
| `cardFaceOf` | `(card) → { kind, label, tone }` | 卡面语义（不含图片本身） | 共用 |
| `decideRevealAnim` | 现有 | 结算动画去重与无障碍 | 共用 |
| `nextAnimStep` | `(state, event) → 动画指令` | 传币 / 水晶 / 落地动画的编排 | 共用 |

一句话：`seatLayout` 输出**归一化坐标**，椭圆形状与半径完全交给各端 CSS——桌面端拉宽、手机端压扁，同一份数据两种观感，不需要第二套布局算法。

## 7. 动效方案

> 判定逻辑已抽成纯函数 [`anims.ts`](../src/client/anims.ts) 的 `planAnims`（比较「上一帧 → 当前帧」的快照，输出该播的动效；11 个单测见 `anims.test.ts`），渲染只消费指令。
> 首帧（挂载 / 刷新 / 热座切视角重建 client）`prev` 为 null → **一律不播**：画面本就是从零渲染，没有「变化」可解释。

| 动效 | 触发点 | 时长 | 状态 |
|---|---|---|---|
| 传币 | `coinHolder` 变化 | 500ms | **已实现**：测量上一位与新持币者的玩家行，硬币沿位移飞过去（`CoinFlight`） |
| 水晶发动 | `crystalsPlaced` 增加 | 800ms | **已实现**：轮次轨道上刚发动的那一枚高亮脉冲 + 技能名与效果浮现。**不做「从席位飞向轨道」的位移**——放上版图后席位与轨道同时显示同一个编号，飞行既多余也不诚实 |
| 回合提醒 | `currentActor` 变化 | 900ms | **已实现**：该座位行做一次金色脉冲，避免漏看「该谁行动了」 |
| 胜负 | `winner` 非空 | 2000ms | **已实现**：旗帜入场 + 金色辉光（纯 CSS，随元素挂载播一次） |
| 翻牌结算 | `lastReveal` 变化 | 5000ms | 此前已实现（3 秒翻牌 + 2 秒飞行，画面已升级为卡面插画） |
| 发牌 | 建局 / 换牌 | 600ms | **延后**：需为每张手牌单独测量与错峰编排，成本明显高于上面几项，放到下一批 |
| 出牌落桌 | `playCard` | 400ms | **延后**：公开前是暗牌，落桌动画要与 5 秒结算动画的时序统筹，放到下一批 |
| 飞入区域 | 结算后分配 | 1000ms | **延后**：现有 5 秒结算动画已把牌飞入「上一轮公开」，区域分配属结算结果的一部分，宜与结算动画一起升级 |

**三条实现原则**：

1. **时序编排抽成纯函数**（`planAnims`），渲染只消费指令——这样动画逻辑可单测，且小程序端能用同一份编排。
2. **一切动效都要能被 `prefersReducedMotion()` 关闭**：JS 侧由 `planAnims` 统一闸掉；纯 CSS 动效（胜负旗帜、轨道高亮、技能浮现、回合脉冲）则包在 `@media (prefers-reduced-motion: no-preference)` 里。不得阻塞操作（现有结算动画的「不可跳过」是规则要求，属例外）。
3. **动画不改状态**：所有动效都是对已发生状态的呈现，不得反向影响 moves（沿用 `RevealStage` 的「纯展示层」约定）。

## 11. 风险与边界

| 风险 | 说明 | 缓解 |
|---|---|---|
| **美术资源来源** | 团队无美术时，插画风很难凭空产出——这是本方案最大的不确定性 | **已定**（§2 决策 10）：AI 生成 → 人工审阅 → PIL 逐像素校验；流程与硬约束见 §5.4。7 张卡面已按此流程产出 |
| **App.tsx 已 1369 行** | 大改中回归风险高 | 步骤 3 先拆分（行为等价），步骤 4 再改视觉 |
| **场景视图的信息密度** | 席位卡空间有限，10 人局 + 手机时标签会挤 | 保留列表式紧凑视图作兜底（§5.2） |
| **动效性能** | 低端手机上多元素同时 transform 可能掉帧 | 只用 `transform` / `opacity`（不触发布局）；提供紧凑模式 |
| **小程序复用预期** | 表现层代码**不能**复用，只有引擎 + 场景函数 + 资源可以 | 本方案已按此预算（§8），不做跨端渲染抽象 |
| **结算动画是规则要求** | 「5 秒不可跳过」已被既有测试与规则约束 | 只升级画面（卡面插画 + 光泽），**不改时长与不可跳过语义** |
| **部署遗漏** | 忘记把 `public/` 加入 Dockerfile 与打包清单 → 线上白图 | 步骤 1 验收里显式包含该检查（§6.4） |
