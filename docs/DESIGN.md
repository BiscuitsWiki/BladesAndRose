# 《血与刃的白蔷薇》线上版 · 设计与技术架构

本文档说明项目的设计思路与技术架构，面向后续开发与维护。

## 1. 项目概览

桌游《血与刃的白蔷薇》的网页轻量版。当前里程碑：

- 完成可复现、可测试的**纯规则引擎**（`src/engine`），覆盖 5–10 人局、夜晚阶段、魔法水晶、出牌与结算全流程。
- 通过**适配层**接入 boardgame.io（`src/client/game.ts`），用其快照与传输能力承载引擎。
- 提供**单页热座** UI 用于本地验证：大厅可自定义角色配比，牌桌可按座位切换视角，界面只渲染该视角过滤后的信息。
- 提供**玩家 UID 身份**（游客 10 位 / 专属账号 9 位）与联机房间：玩家可凭 UID 收回自己的座位，回到主页时会被自动拉回「进行中」的对局继续游戏。

本版仍不做：数据库、匹配、聊天。房间与对局状态仅存于进程内存（服务重启即清空）；只有**账号表**落盘在 `data/accounts.json`（见第 5 节）。

## 2. 技术栈

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 语言 | TypeScript | 全量类型约束，`npm run build` 前先 `tsc --noEmit` |
| 构建 | Vite | 开发服务器 5173 端口，`host: true` 便于局域网调试 |
| 前端 | React 18 | 函数组件 + hooks，无路由库，用 URL hash 保存大厅参数 |

| 状态不可变 | immer（boardgame.io 内部依赖） | master 端 move 收到的是 immer draft，引擎提供就地接口适配 |

## 3. 总体架构

分为三层，依赖方向单向向下，引擎层不依赖任何框架：

```
┌─────────────────────────────────────────────────────────┐
│  表现层  src/client/App.tsx（壳）· lobby/ · room/ · board/ · scene.ts · styles.css │
│  大厅（人数/配比/座位）、房间面板、牌桌渲染、热座视角切换、场景纯函数       │
└──────────────────────────┬──────────────────────────────┘
                           │ moves / GameView
┌──────────────────────────▼──────────────────────────────┐
│  适配层  src/client/game.ts                               │
│  把引擎包装为 boardgame.io Game：moves、playerView、        │
│  endIf、activePlayers、game 对象按配比缓存                  │
└──────────────────────────┬──────────────────────────────┘
                           │ applyMoveInPlace / playerView / createGame
┌──────────────────────────▼──────────────────────────────┐
│  引擎层  src/engine/                                      │
│  纯 TypeScript 规则状态机，零框架依赖，可独立测试            │
│  types · config · setup · game · magic · round · view · rng │
│  autoPlay（AI 托管决策）                                     │
└─────────────────────────────────────────────────────────┘
```

设计动机：规则引擎与宿主框架解耦。引擎可以作为纯函数库直接单测（当前 132 个用例），将来替换传输方式（socket.io）或接入 AI 座位时，无需改动规则代码。

## 4. 引擎层设计

### 4.1 文件职责

| 文件 | 职责 |
| --- | --- |
| `types.ts` | 核心类型：`Role`/`Faction`/`Card`/`PlayerState`/`Zones`/`Knowledge`/`RoundModifiers`（本轮效果）/`RevealResult`/`Phase`/`GameState`/`Move` |
| `config.ts` | 规则数据：角色分布、胜负阈值、技能表（展示数据）、技能组（loadout）预设与校验 / 签名、自定义配比的合并/校验/签名 |
| `setup.ts` | `createGame()`：建局（含技能组解析）、发牌、发水晶、自动结算夜晚阶段 |
| `game.ts` | 动作入口：`applyMove`/`applyMoveInPlace`、8 种动作的校验与执行、`autoAdvance` 自动推进（决策点见 §4.4） |
| `magic.ts` | 技能插件表（`SkillId → 效果函数`，只写「本轮效果」字段）、动态目标解析（`resolveTargets`）、邻位定义、目标合法性校验、出牌基准顺序 |
| `round.ts` | 每轮公开结算（`resolveReveal`，多圈出牌时逐张展开）与胜负判定（`finishRound`） |
| `view.ts` | `playerView()`：隐藏信息过滤，生成每位玩家可见的 `GameView`（含技能组与动态目标池） |
| `autoPlay.ts` | `autoMoveFor()`：AI 托管 / 自动代打的决策（只读状态、可注入随机源），返回一个 `Move` 或 `null` |
| `rng.ts` | mulberry32 可序列化随机数：`nextInt`/`shuffleInPlace`/`pickRandom` |
| `index.ts` | 引擎公共 API 出口 |

### 4.2 状态模型

单一状态对象 `GameState` 即整局快照，**完全可 JSON 序列化**（无类实例、无函数、无引用外泄）。关键字段：

- `players[]`：id、座位、角色、阵营、手牌、水晶编号、水晶是否已放上版图（角色/手牌/水晶属于隐藏信息）。
- `skills`：本局技能组（水晶槽 1-12 → 技能 id），建局时从 `setupData` / 本地参数解析并固化，是技能的唯一权威（`skillOfCrystal(crystal, state.skills)`）。
- `order`：顺时针座次；左右邻由此推导。
- `coinHolder` / `round` / `phase`：阶段机位置与当前持币者。
- `zones`：版图五区 —— `whiteRose`（白蔷薇区）、`sacrifice`（献祭区）、`death`（死亡区）、`blade`（血刃区）、`ghosts`（幽魂弃牌堆）。
- `crystalTrack` / `crystalsPlaced`：已翻开的全部水晶（编号是公开信息）。
- `modifiers`：本轮效果集合（初版：顺序公开、强制出牌、强制随机、强制跳过、行动绑定、殿后、换牌；2025 扩充：随机出牌、圈数、同出集合、三张即开阈值、司教必出旗标、禁幽魂、公开前补出——全部只是「数据字段」，流程代码只读字段）。
- `pendingMagic`：需要指定目标的技能挂起态（技能、水晶编号、决策者）；动态目标池与必选数由 `resolveTargets` 按实况解析。
- `pendingRedraw`：10 号换牌挂起态——已被指定、等待自己完成对调的玩家（此时仍处于 `play` 阶段，复用选牌界面；换牌 = 选中的手牌与打出的牌对调，原牌收回手中）。
- `playOrder` / `turnIndex` / `lap` / `playSequence` / `played` / `extraPlays` / `passed`：出牌阶段调度与结果（`lap` 记录第几圈，扩充 4 号两圈出牌；`extraPlays` 存同轮第二次及以后打出的牌；`passed` 记录本轮谁已跳过，属公开信息，用于区分「跳过」与「尚未行动」）。
- `lastReveal`：最近一次公开结果。
- `knowledge`：按玩家存放的私有情报（夜间同组名单、暗刃侦查、窥牌）。
- `rngSeed`：随机种子，保证整局可复现。

### 4.3 纯函数状态机

8 种动作构成闭集（`Move`）：

| 动作 | 触发者 | 含义 |
| --- | --- | --- |
| `passCoin` | 持币者 | 交出硬币，翻开受币者的水晶 |
| `resolveMagicTargets` | 魔法决策者 | 为需要目标的技能指定玩家（人数由 `resolveTargets` 动态解析） |
| `chooseGoLast` | 殿后持有者 | 在自己的回合选择最后行动 |
| `playCard` | 当前行动者 | 出一张手牌（10 号换牌挂起时用于完成对调；随机出牌轮会被拒绝） |
| `playRandom` | 当前行动者 | 3 号扩充：选择出牌但由引擎随机抽牌（不接受 `cardId`） |
| `passTurn` | 当前行动者 | 跳过（无手牌时引擎自动跳过） |
| `pickPreShuffleTarget` | 补出决策者 | 6 号扩充：公开前指定一名未出牌玩家随机补出一张 |
| `resolveRedraw` | 换牌持有者 | 公开前指定一人由其自己换牌，或放弃 |

两个入口：

- `applyMove(state, move)`：先 `structuredClone` 再执行，**保证不修改入参**，用于纯逻辑测试与未来非 immer 宿主。
- `applyMoveInPlace(state, move)`：就地修改，专门适配 boardgame.io/immer 的 draft（Proxy 对象无法被 `structuredClone` 复制）。动作内部抛错时由宿主回滚整次修改。

所有动作先做前置校验（阶段正确、是当前行动者、目标合法……），非法即抛错，绝不静默产生脏状态。

### 4.4 阶段状态机与自动推进

```
magic ──passCoin──► magicTargets ──resolveMagicTargets──► play
  ▲                    （仅需指定目标的技能）              │
  │                                                      ▼
  └──── startNextRound ◄── finishRound ◄── resolveReveal ◄┘
                                    ▲                     │
                                    │    prePick ◄────────┤（6 号扩充：公开前补出，池空则跳过）
                                    │    redraw ◄──────────┘（10 号效果挂起时）
```

`autoAdvance` 负责推进一切**无需玩家决策**的步骤，避免 UI 出现无意义按钮。对应技能方案里的「流程决策点」：

- **决策点 1（参与者集合）**：`trio` 集合（扩充 5 号）生效时把非集合玩家从 `playOrder` 剔除——自动跳过、不询问；
- **决策点 2（自动动作）**：无手牌的玩家自动跳过；被 3/4 号效果指定的玩家由引擎随机代打；被强制跳过的玩家直接跳过；被 5 号效果绑定的后行动者自动跟随先行动者；
- **决策点 3（合法性守卫）**：出牌/跳过分别校验（被指定跳过、随机出牌轮拒绝显式选牌、禁幽魂、司教持牌不得跳过）；
- **决策点 4/5（收束条件）**：达「三张即开」阈值立即收束；否则计划顺序走完且圈数走完（扩充 4 号两圈）；
- **决策点 6（公开前插入）**：结算前暂停进入 `prePick` 等补出决策（目标池为空则无事发生）；
- 收束后自动进入换牌 / 公开结算，并衔接下一轮。

循环带 10000 次护栏，异常时抛出「自动推进陷入死循环」以便早期暴露规则漏洞。

### 4.5 确定性随机

禁用 `Math.random`，统一走 `rng.ts` 的 mulberry32：种子存活在 `GameState.rngSeed` 里，随快照一起序列化。同一局面 + 同一动作序列 ⇒ 同一结果，方便复盘与测试断言。

### 4.6 隐藏信息与 playerView

安全边界只开一个口：`playerView(state, viewerId)`。规则：

- 他人只下发公开字段：`handCount`、`crystalPlaced`、本轮是否已出牌 / 是否跳过（`played`、`passed` 布尔值，不含牌面）。
- 角色、阵营、手牌内容、水晶编号仅本人可见。
- `lastReveal.byPlayer`（谁出了什么）**只有在 2 号效果「顺序公开」时才是公开信息**，匿名公开时一律不下发空对象，否则等于把所有人的出牌当场点破。
- `knowledge` 只取该玩家自己的条目；夜间同组名单只对组内玩家本人可见，引擎不提供任何「一键公开」动作（是否公开由玩家在桌上自行交流决定）。
- `log` 是公开信息，因此引擎不写任何会泄露身份的条目：双刃的夜间换牌只作内部结算、不落日志（回归测试断言建局日志不含「双刃」）。
- 公开结算每轮记录「出牌情况」：`lastReveal` 新增 `coinHolder`（本轮持币者）+ `playStatus`（从持币者起按座位顺序的 `{ id, played }[]`），只含 `played` 的二元状态（已出牌 / 跳过）、**不含牌面与角色**，因此与是否顺序公开、是否洗混无关。同一份数据两处呈现：公开日志追加一行 `第 N 轮出牌情况（自持币者 X 起顺时针）：…`，并随「上一轮公开」面板展示；无人出牌的轮次同样记录与写日志（该轮面板不渲染）。顺序必须取 `orderFrom`（`setup.ts`）而非 `playOrder` / `playSequence`——后两者会被 6 号殿后与 10 号换牌改写，且会把匿名模式的出牌顺序变成公开信息。
- 所有卡牌经显式深拷贝（`cloneCard`）后下发，且不使用 `structuredClone`——playerView 也可能运行在 immer draft 上。

### 4.7 游戏规则

游戏规则的完整说明独立成文档：[RULES.md](./RULES.md)（角色配比与胜负阈值、卡牌与准备、阶段流程、12 枚水晶技能、公开结算与胜负判定、隐藏信息）。本文档不再复述规则细节，只保留一条与状态模型强相关的实现事实：

- **水晶 = 技能指针，技能组决定指针表**：水晶编号与发动顺序无关；N 人局恰好 N 轮，每轮由受币者发动自己的水晶。对局技能组（`GameState.skills`，12 槽）在**建局时固化**——它把编号映射到技能，同一技能可占多槽（初版 1≡12；扩充 11≡2、12≡1）。技能实现为「插件表」：展示数据在 `config.ts` 的 `SKILLS`，效果函数在 `magic.ts` 的 `EFFECTS`（只写 `RoundModifiers` 字段 / 知识 / 牌区），流程代码只读字段、永不过问技能版本；目标规格（静态 `oneOther…` 与动态池）统一由 `resolveTargets(state, skill, chooser)` 解析，引擎校验、客户端选择 UI、AI 托管三处共用。两套预设见 [RULES.md](./RULES.md) 第 11 节。

## 5. 适配层设计（boardgame.io）

适配层的核心立场：**调度权完全归引擎，boardgame.io 只负责快照与传输**。几个关键决策：

- **不使用 turn/phases 调度**。行动顺序全部由引擎的 `currentActor(G)` 决定。
- **`activePlayers: { all: true }`**。master 在执行动作前会调用 `isPlayerActive` 校验；缺省时该判断退化为 `playerID === ctx.currentPlayer`（恒为 `'0'`），导致除 0 号座位外所有动作被 master 拒绝（player not active）。声明全员 active 以放行。运行时必须传 `all: true`，但官方类型声明不接受 `true`，故做了显式类型收窄。
- **每个 move 都 `noLimit: true, client: false`**：
  - `noLimit`：关闭动作计数，否则默认 `maxMoves=1` 会在一次出牌后自动 EndStage，把人踢出 activePlayers；
  - `client: false`：禁止客户端乐观执行。客户端只有过滤后的视图（看不到他人手牌/水晶），引擎在其上无法运行，乐观执行必然失败并刷 "invalid move"。所有动作只由 master 执行，再回传结果。
- **`INVALID_MOVE`**：引擎抛出的规则错误被捕获并转为 `INVALID_MOVE`，由 immer 回滚本次修改。
- **game 对象按配比 + 技能组缓存**：`Local()` 传输器把 game 对象的**引用**当作 master 的缓存键。因此 `getBladesAndRose(override, loadout)` 按「配比签名（+ 热座技能组签名）」复用同一个对象（同配比重设后能继续原局；热座换技能组会重新建 client 与 master），不同配比 / 技能组返回新对象（不会读到旧配置遗留状态）。联机的技能组不经过客户端本地参数，由服务器经 `setupData` 带入（优先级高于本地参数）。
- **传输层可切换**：默认 `Local()`（单页热座）；URL hash 带 `room` 时改用 `SocketIO` 连接开发用房间服务器（`src/server/dev-server.ts`），`matchID` 即房间号——相同 `room`、相同人数与配比、不同 `seat`（playerID）的多个客户端共享同一局。自定义配比经 game 变体承载：`gameNameOf` 按配比签名生成 game 名称（同时是 socket.io 命名空间），服务器为全部 480 种合法配比各注册一个变体，配比不同的玩家因此天然进入不同对局。**对局由服务器在首个座位认领时建局**（见下方「服务器侧建局」条），进程内存存储；座位认证见下条。
- **房主与座位号无关**：房主 = 创建房间的玩家，服务器在房间内存表里记录 `hostSeat`（首次由最小已入座座位推得——最先入座者就是创建者）。房主专属操作（改名 `/room-name`、开局 `/room-start`、重开 `/reset-room`、转移房主 `/room-host`）一律以服务器解析出的房主为准，不再硬编码座位号。房主可把房主转给任一已入座玩家（`/room-host`，需房主凭据）；**房主换座**时客户端按「先 `join` 新座位 → 用旧座位凭据把房主带到新座位 → 再 `leave` 旧座位」的顺序执行，旧座位在转移完成前一直有效，因此不出现房主真空期、也不会被顺位规则误判。**房主离座 / 座位换人**（房主身份绑定在「座位号 + 该座位的凭据」上）：立即顺位给最小已入座且在场的座位，**不给宽限**——否则空出的房主座位被新入座者坐走会「继承」房主；只有**房主仍坐在原座位但断线**（刷新 / 掉线，boardgame.io 的 master 会把连接状态写进房间元数据的 `isConnected`）才宽限 15 秒，超时仍未回来才顺位。「重开」删除整个房间（`/reset-room`，内置 `leave` 在有凭据的房间只退出自己，不足以清空），并把 `started` 与 `hostSeat` 一并复位，由重新入座者按上述规则重新推得房主。
- **座位认证**：联机入座先经 lobby 接口 `join` 拿到该座位的 `playerCredentials`（存本机 localStorage，刷新自动重连）。房间内一旦有玩家持有凭据，之后所有连接与动作都必须携带与座位匹配的凭据——冒用他人座位会被服务器拒绝；换设备 / 清除凭据后无法顶替已占座位（需换座位或由房主重开）。换座 = 先加入新座位再释放旧座位（见上条）；观战席不需要凭据（`playerID = null` 连接，只收公开视图）。房间名、观战者心跳（60 秒过期）与房间码存于开发服务器的内存表。房间另有「等待开局 / 已开局」状态（`started`，同为内存表）：进入房间先只显示座位面板，房主点「开始游戏」（自定义端点 `/room-start`）后，其余客户端经 3 秒轮询看到 `started` 才显示牌桌；开局前牌桌客户端保持连接但隐藏（座位凭据校验、刷新重连与自动建房照常工作）。**坐满才能开局**：`/room-start` 校验房间里每个座位都已占用，未坐满返回 409（附空座位清单），客户端在未坐满时直接禁用「开始游戏」按钮。理由：空座位在引擎里永远不会行动——`playOrder` 覆盖全部座位（`orderFrom`）、阶段一只推进真人 / 托管，而 AI 托管只认 presence 里已托管的座位（= 曾入座后断线），救不了从未有人坐的空座；「暗刃 / 白蔷薇各必须有且仅有 1 名」也意味着关键身份落在空座位时游戏直接失义。人凑不齐时改人数的唯一路径是房主「重开」——它删除整个房间、重新进入即按新配置建房（人数与配比固化在 game 变体名与建局时的 `numPlayers` 里，`/seat-claim` 的兜底只补技能组、不改人数）。
- **服务器侧建局与房间技能组（setupData 通道）**：技能组不在客户端决定——`/seat-claim` 在对局不存在且请求带 `count` + `gameName` 时，服务器取 `roomExtras.loadout` 组 `setupData`，经 `boardgame.io/internal` 的 `createMatch`（内含 `validateSetupData` 与 `InitializeGame`）生成 `{ initialState, metadata }` 后落库（`server.db.createMatch`），再继续座位认领。不用 REST `/games/:name/create` 的原因：它的 matchID 由库生成 uuid，无法使用本项目的 6 位房间码；而 InMemory 存储会把 `initialState` 同时写入 `state`，预建的对局不会被随后客户端 socket 同步时的「按需自动建房」覆盖。兜底规则：对局已存在但技能组与房内不一致（旧客户端「空连接自动建房」留下的初版对局）时，**原地补写**技能组（同上机制）；补不了（已开局 / 已有人行动）就维持现状——**任何情况下都不再清局踢人**。房间技能组由房主修改：`POST /room-skills`（房主凭据校验；仅未开局，对局中提示先「重开」）——把新技能组**原地写进对局**（`state.G.skills` 与 `metadata.setupData`，`db.setState` + `db.setMetadata`），**不清局、不动座位 / 凭据 / 房主记录 / UID 绑定**：所有玩家留在房间里、无需刷新；已连接客户端由 `/room-info` 的 `skillset.sig` 变化触发「重建 client = 重新同步」刷新牌桌（开局前牌桌本就隐藏，整个过程对玩家不可见）。补写只允许用于「尚未开局且尚无人行动」的对局，否则 409。可行性依据：boardgame.io 的 master **每次同步 / 动作都从存储重新读取状态**（见 master.onUpdate），所以写回后新同步立即读到、后续动作也不会覆盖。旧客户端（不带 `count`/`gameName`）仍走「no-match → 空连接自动建房」降级路径，只会拿到初版技能组。`/room-info` 的 `skillset` 字段（预设标识 + 显示名 + 技能组签名 `sig`：客户端据此检测变化并重连刷新）供房间面板展示。
- **身份与座位绑定（UID）**：玩家有系统发放的唯一 UID——游客 10 位（`1000000000–9999999999`）、专属账号 9 位（`100000000–999999999`），按数值区间区分（`src/server/accounts.ts`）；账号表落盘 `data/accounts.json`（scrypt 加盐哈希，注册 / 登录取回同一 UID），服务器重启后账号不丢、房间仍清空。座位 ↔ UID 绑定记在**服务器内存表** `roomExtras.uids`，**不写进房间元数据**——boardgame.io 的 `filterMatchData` 只剥离 `credentials`，其他字段（如 `players[].data`）会广播给房间内所有客户端，等于把「可顶替座位」的 UID 泄露给同房玩家。带 UID 的入座走自定义端点 `POST /seat-claim`（决策表见 `src/server/seats.ts`）：座位是本 UID 的 → **归还现有凭据（不轮换）**，保住「同 UID 两窗口同座位共存」与 `hostToken` 的有效性；空座位 → 写名字 + 生成新凭据（随机串即可，boardgame.io 只做字符串相等比较）并绑定；已被其他 UID 占用 → 403；旧房间未绑定 UID 但凭据对得上 → 补绑。不带 UID 时客户端回退到内置 `join`（降级路径）。`GET /room-info/:id?uid=` 额外返回 `mySeat`（只回自己的座位，不下发他人 UID）。
- **座位表防原型污染**：房间元数据的座位表（`metadata.players`）在**建房时被换成无原型对象**（`Object.create(null)`），且一切以座位号为键的读写都先过 `isSeatKey`（自有键 + 纯数字，见 `src/server/seats.ts`）——`/seat-claim`、`/room-name`、`/room-start`、`/room-host`、`/reset-room`、`/active-game` 均已接入。原因：boardgame.io 内置的 `join` / `leave` 直接以 `playerID` 为键读写 `players`（`players[playerID]`），传入 `__proto__` / `constructor` 这类原型链键会读到 `Object.prototype` / `Object` 函数（不是 undefined），随后写入 `name` / `credentials` 就会落到原型上，造成**进程级原型污染**：所有空座位被读成「已占用」、凭据校验读到注入值。修复后这类键一律按「座位不存在」拒绝（库端点 404、自定义端点 404 / 403），正常座位与降级路径（内置 join）不受影响。
- **回到主页自动拉回**：客户端启动时若 URL 无 `room`（「主页 / 大厅」状态）且不是热座 URL，先确保有身份（没有就领游客号）再调 `GET /active-game?uid=`：该 UID 有**已开局且未结束**的对局（判定复用巡检的 `isGameInProgress`）→ 自动 claim 该座位并进入牌桌（多局并行取 `updatedAt` 最新的一局）；没有 → 留在大厅。等待开局 / 已结束的房间不自动拉回（仍可从大厅手动进）。配比从服务器返回的 game 变体名反解（`distributionOfGameName`，与 `gameNameOf` 互逆），无法识别时回大厅并提示。`#lobby=1` 是跳过自动拉回的逃生阀（调试用）。
- **断线处理（未开局 1 分钟 / 对局中保座 + AI 托管）**：在座玩家断线时，其座位在房间面板上变灰（`/room-info` 的 `offline` 列表 + 座位号后标「 · 断线中」）。
  - **等待开局（或对局已结束）**：断线超过 1 分钟仍未重连 → 服务器按「退出房间」处理：释放该座位（清掉名字与凭据，**对局状态不动**，回来重新入座即可继续）；若房里因此再没有在座玩家，对局一并清掉并转入空置留存倒计时。客户端轮询到自己的座位空出（断线超时被释放、或对局被清空）时会**自动重新入座**（必要时先重新建房），座位已被别人占走则转入观战席并提示；若整个房间已不存在（空置超时销毁 / 房间服务器重启过），退回大厅并提示重新创建。
  - **对局进行中**：座位**一直保留到本局结束**，不按 1 分钟释放。断线超过 3 分钟仍未回来 → 服务器把该座位标记为 **AI 托管**（`/room-info` 的 `ai` 列表，面板与牌桌玩家行标「 · AI 托管」），由巡检定时器以该座位的身份代操作：阶段一传币随机交给一名水晶未放上版图的玩家、技能选人按目标约束随机选取、阶段二一律跳过（被规则强制出牌时改打手中第一张牌）、10 号换牌阶段放弃使用（决策逻辑是引擎里的纯函数 `autoMoveFor`，可单测）。AI 代打直接向 socket.io 命名空间发 `update` 动作、不做 `sync`，因此既不会被算成「该座位已连接」（`isConnected` 全程保持 false），也不会触发 master 的在线状态广播；**本人回来**（下一次巡检看到在线即可，无需连续确认）立即撤销托管、恢复正常操作。
  - 「在线 / 托管」由服务器自己在房间内存表里按座位记录（`presence`：断线起点 + 托管标记），牌桌的玩家行优先显示这份真值，`matchData.isConnected` 只作为兜底。
- **空房间留存（3 分钟）**：房间里没有任何「在座且在线」的玩家时（都断线 / 都离座 / 还没人入座），服务器把它记为空置并开始倒计时（`roomExtras.emptySince`，后台每 5 秒巡检一次，在线状态维护、断线处理、空房回收与 AI 代打共用同一趟巡检，不依赖任何客户端还在线）；期间有人重新入座 / 连回来 → 倒计时清零、房间继续存活，第一位入座者按房主规则成为房主；期满仍无人 → 销毁房间（清掉对局与房间信息，房间码失效，进入时提示「房间不存在（或已销毁）」）。**对局进行中暂停销毁**：即使全员暂时断线也保留房间与对局（AI 会继续代打），等玩家回来或本局结束。若房间里已没有对局（如全员断线被释放、房主重开后没回来），开局状态与房主记录会一并复位——接手者需重新点「开始游戏」。`/room-info` 的 `retained` 字段让大厅放行留存期内的空房间（进入即重新建房开局）。
- **`disableUndo: true`**：隐藏身份游戏不允许悔棋。
- **`endIf`**：`G.winner` 非空即结束，胜负原因随 `winReason` 一并给出。

## 6. 表现层设计

> 改造计划见 [UI-OVERHAUL-PLAN.md](./UI-OVERHAUL-PLAN.md)（2D 插画风精美化：桌椅场景、角色卡面、动效与音效；引擎与联机不动）。本节描述的是**当前**实现。

- **大厅**（`App.tsx` → `Lobby`）：选择人数（5–10）→ 编辑角色配比（每行显示官方值、± 步进、合计校验、一键恢复官方；白蔷薇与暗刃固定为 1 名、不可调；阈值仍按人数取官方值）→ 顶部以「你的昵称」输入自己的显示名（与房间无关，仅联机显示用，记在本机）→「本地热座」区块先选**技能组**（初版 / 2025 扩充包，仅本地生效），再选座位，或用「创建房间 / 进入房间」走联机（创建时先填房间名称，房间号由系统随机生成、不可编辑；进入时填房间号即可；自动坐上空位，坐满则进观战席）。参数写入 URL hash（`#players=..`，联机附 `room=房间号`，自定义配比附 `d=配比签名`，观战为 `spectate=1`），刷新后原样恢复。
- **身份条与启动检查**（`AccountBar.tsx` + `App.tsx`）：大厅顶部显示当前身份（「游客 · UID 1000000001（10 位）」/「专属账号「Alice」· UID 123456789（9 位）」）并可一键复制 UID（图标复制，成功变对勾）。游客提供「注册 / 登录」（内联小表单：用户名 + 密码，回车即提交），专属账号提供「退出登录」——退出后立刻换回新的游客号；注册 / 登录成功后若昵称为空则默认填用户名（不覆盖已有昵称），并尝试拉回该 UID 进行中的对局。处于「主页」状态（URL 无 `room`）启动时先渲染「正在检测进行中的对局…」面板（避免白屏），检查完再决定进牌桌还是留在大厅；联机顶栏也显示只读 UID 格子（可复制）。
- **牌桌**（`Board.tsx`）：
  - 顶栏（联机）：房间名与房间号各是一个圆角「格子」（chip），格内右侧带图标——复制图标点击即复制、成功后短暂变对勾（Clipboard API，局域网 http 下退化为 execCommand）；房主在房间名格内另有铅笔图标，点击进入内联编辑（回车保存 / Esc 取消）；房主还有「重开」。
  - 房间面板（联机）：座位格子——头像（昵称派生色 + 首字）与昵称，下方标座位号，房主的座位标「· 房主」（房主由服务器记录，与座位号无关）；断线中的座位格子变灰并标「· 断线中」，被 AI 托管的座位标「· AI 托管」（悬停分别说明：未开局 1 分钟按退出处理 / 对局中保留到本局结束、超 3 分钟由 AI 暂时托管、本人回来自动恢复）；点空座位即入座 / 换座（先加入新座位、房主则顺带转移房主身份，再释放旧座位）；下方为观战席名单（60 秒心跳）。数据每 3 秒向房间服务器轮询；换座 / 开局 / 转移房主成功后立即刷新一次（不必等轮询），换座请求进行中格子先禁用并显示「正在切换座位…」。房主在面板里还有「转移房主」：点击进入转移模式，格子切换为「选择目标」（已入座且非自己的座位高亮可点），选中即把房主转过去。开局前房主看到「开始游戏」按钮（未坐满也能开始，空座位本局不会行动），其他玩家看到「等待房主（座位 N）…」提示，牌桌位置只显示「等待开局」面板；开局后座位锁定（空座位不再可点）、面板保留在牌桌上方。面板另有「技能组」行：显示房内当前技能组（来自 `/room-info` 的 `skillset`）；房主在未开局时可直接改（预设二选一 + 「保存技能组」，二次确认弹窗说明「只影响尚未开始的对局；所有玩家无需刷新」）——服务器原地写入对局技能组（不清局、不踢人），各客户端轮询到 `skillset.sig` 变化后自动重建连接（= 重新同步）刷新牌桌。
  - 玩家行：左侧是眼睛标记槽位——睁眼玩家的视角里由系统按夜间情报直接标注（同组为睁眼、组外为半透明「闭眼」，不可修改）；非睁眼玩家的视角默认显示半透明「闭眼」，点击在「闭眼 ⇄ 睁眼」间切换自己推断的标注（仅本机记录、按视角各记一份，不进 `GameState`）；观战席该槽位留空，不显示任何睁眼/闭眼信息。随后是头像 + 昵称（联机取 join 时填写的昵称——来自 boardgame.io 下发的 `matchData` 玩家数组，日志中的「玩家 N」同样替换为昵称）、座位号、「(你)」固定槽、手牌矩形（0 张置灰）、六边形水晶（已释放置灰）；行末标签区里持币者用银色硬币图案标记，「已跳过」浅灰、与金色「已出牌」区分；玩家断线时整行变灰并在标签区标「断线中」，若该座位已进入 AI 托管则改标「AI 托管」（联机以房间服务器下发的 `offline` / `ai` 名单为准——AI 代打时的短暂连接会让 `matchData.isConnected` 闪现在线；服务器数据还没回来或热座时才回退到 `matchData`）。
  - 观战：以 `playerID = null` 连接，服务器只下发公开视图（他人角色/手牌/水晶与全部私有情报都不下发）；眼睛列隐藏；玩家面板提供「观战视角」切换（仅高亮关注的座位）；「你的手牌」面板不渲染。
  - 游戏进程：独立面板，位于版图与玩家区之间，描述当前步骤（等待谁行动 / 轮到你做什么）并汇总轮次、阶段与持币者；底部为「轮次」次级标题与 N 个轮次水晶六边形（随水晶发动按顺序填充编号，已发动的水晶与玩家区一样为浅灰填充，悬停显示发动者），轨道下方显示本轮已发动水晶的编号、技能名与效果说明（尚未发动时不显示），「重开一局」按钮位于标题行右侧（仅热座；联机模式由房主在顶栏操作）；轮到自己时金色高亮。
  - 扩充技能交互（2025 技能组）：目标选择统一走引擎下发的 `pendingMagic.pool`（动态目标池）+ `needTargets`（必选数，可能为 0——此时显示「没有可选目标，确认」）；3 号轮手牌不可选、出现「随机出牌」按钮（点击即由引擎抽牌）；6 号轮新增「公开前 · 指定补出者」阶段，玩家行可直接点选未出牌且有手牌者；8 号轮司教本人视角在「你的手牌」面板看到「必须出牌」提示（他人视角无任何标记，身份不泄露）；9 号轮幽魂牌置灰并提示「本轮不能打出幽魂牌」；4 号轮在阶段行显示「出牌第 X/2 圈」，公开结算按实际牌数逐张翻牌（最多 2N 张）。
  - 版图区：三栏布局 —— 左列以「献祭区」为分组标题（内含「白蔷薇」「普通花苞」两格），中间以「弃牌区」为分组标题（内容只统计幽魂，无则显示「无」），右列以「血刃区」为分组标题（内含「血刃」「死亡花苞」两格）；分组标题加粗放大、下有亮色分隔线，每格带独立边框。各格均显示进度：白蔷薇「✿ 已收集 / 本局白蔷薇牌数」（白色）、普通花苞与死亡花苞「❀ 花苞数 / 阈值」（金色）、血刃「⚔ 已打出 / 本局血刃牌总数」（红色，总数经 `playerView` 的 `cardTotals` 下发）。
  - 上一轮公开：匿名公开时只展示洗混后的牌面；2 号「顺序公开」生效时按出牌顺序展示，并在每张牌下方标注出牌者；牌面下方附「出牌情况」：第一行为「出牌情况（自持币者 X 起顺时针）」，第二行起为名单（玩家 X 已出牌、玩家 Y 跳过……），「已出牌」金色加粗、「跳过」灰白——只记状态、不含牌面。
  - 结算动画（`RevealStage.tsx` + `revealAnim.ts`）：每次公开结算播放一幕**严格 5 秒、不可点击跳过**的动画——前 3 秒全屏弹窗内所有公开牌同时缓缓翻正，后 2 秒这些牌缩小飞向「上一轮公开」面板并高亮它（高亮恰好动画结束时最亮）。动画是纯客户端展示层（不进 `GameState`、不影响联机同步）；只在观察到「新的结算轮次」时播放——刷新 / 中途加入 / 切换视角不重播，重开一局后复位（决策抽成纯函数 `decideRevealAnim`，配套单测）；`prefers-reduced-motion: reduce` 的用户整幕跳过。
  - 私人信息面板：本人角色、手牌、水晶编号，以及该水晶对应的**技能名称与效果描述**（编号本身只是指针，玩家需要知道效果才能决策）。
  - 操作区：出牌阶段的「跳过」「我要最后行动」与「确认出牌 / 取消」均在手牌面板（选中手牌后确认出牌或取消，未选中时可直接跳过或选择殿后），换牌阶段的「放弃换牌」在玩家区；10 号换牌挂起时，手牌面板的确认按钮变为「确认替换」、玩家行标注「必须换牌」，跳过与「我要最后行动」不可用，步骤文案改用换牌表述；需要指定目标时按 `pendingMagic.targets` 约束过滤可选玩家。
  - 卡牌标记：白蔷薇用白色蔷薇 ✿，司教/信者用花苞 ❀，血刃用 ⚔，互不混淆。
- **热座限制**：`Local()` 传输器不支持跨标签页同步，因此本地验证采用单页热座——在同一页面切换视角替不同座位行动，切换时其他玩家应回避。
  - **切换视角 = 重建 client**（不是 `updatePlayerID`）：boardgame.io 0.50.2 的 Local 传输器按 playerID 累积回调且永不注销，master 的 `sendAll` 会把同一状态给所有访问过的座位各发一份、最后由「座位号最大者」覆盖写入同一个 store——状态一推进，当前视角就可能拿到别人的过滤视图（表现：「你的手牌」面板消失、无法出牌）。重建 client 后过期回调落在已卸载的旧 client 上，当前 client 只收自己的视图（对局不受影响：Local master 按 game 对象缓存，新 client 重新同步到同一局）。回归测试见 `client-smoke.test.ts` 的「热座切换视角」用例。
  - 「睁眼」标注因此提升到 **App 层**持有（Board 会随 client 重建而重挂），切换视角不丢标注。
- **移动端**：`max-width: 560px` 媒体查询调整页边距、列数、卡牌尺寸与字号；公开结算动画的弹窗与牌尺寸一并压缩（每行 4 张，10 人局 3 行）。

## 7. 数据流

```
用户点击
  │  client.moves.xxx(args)
  ▼
boardgame.io Client ──Local() 传输──► master
  │                                    applyMoveInPlace(G, move)  ← immer draft
  │                                    校验失败 → INVALID_MOVE（自动回滚）
  │◄────────── 新 G + playerView(G, seat) ──────────┘
  ▼
React 仅渲染过滤后的 GameView（GameView 类型即 UI 的输入契约）
```

## 10. 已知限制与演进方向

- **在线多人**：开发用房间服务器（`npm run dev:server`，socket.io）已支持多开测试——房间码由服务器生成，座位凭据存于本机浏览器（刷新自动重连、冒用他人座位被拒绝），座位格子可入座 / 换座，满员自动进观战席（观战只收公开视图）。仍属开发工具：玩家身份见下条（UID 账号），房间名 / 观战名单 / 房间码与「座位 → UID」绑定均存于进程内存（服务重启即清空），观战者名单靠 60 秒心跳近似；生产化还需房间列表与持久化等；引擎与适配层的 moves/playerView 契约保持不变。
- **账号与持久化**：账号表（UID、用户名、scrypt 盐与派生值）落盘 `data/accounts.json`，服务器重启后注册 / 登录仍取回同一 UID；房间与对局状态仍只在进程内存（服务重启即清空，第一版约束）。**已知限制**：UID 即身份、开发版允许知道 UID 就顶替座位（无口令二次校验、无速率限制与风控）；游客清除浏览器数据即换新号，旧座位无法收回（符合游客语义）；账号文件是明文 JSON（但密码只存盐与派生值，不存明文）；将来 `git init` 时把 `data/` 加入 `.gitignore`（含账号数据，不应入库）。
- **AI 座位**：已实现「断线托管」版——对局进行中在座玩家断线超 3 分钟后，服务器以该座位的身份代打（引擎纯函数 `autoMoveFor`：传币随机、技能选人随机、出牌一律跳过），本人回来即撤销；代打走 socket.io 的 `update` 动作、不做 `sync`，因此不会污染在线状态。**主动添加 AI 玩家**（开局就有机器人占座、可正常跑完一整局）仍未实现；引擎是无副作用的纯函数，同一套「枚举合法动作 → 启发式/搜索选优 → 生成 Move」的接法可以直接复用。
- **boardgame.io 版本锁定 0.50.2**：维护频率低，升级前需回归适配层测试。
